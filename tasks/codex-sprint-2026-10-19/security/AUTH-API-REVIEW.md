## Confirmed findings, ranked

### F1 — P1: public player reads can invoke a service-role writer

Evidence: `web/lib/NHL/server/index.ts:105-117` reads the public current roster and, on a missing row, invokes `updatePlayer(id, supabaseServer)` before throwing. `web/pages/api/v1/db/update-player/[playerId].ts:30-52` fetches NHL player data and upserts `players`. Its default endpoint's `adminOnly` wrapper at line 7 does not wrap this separately exported function.

Public entry points are `web/pages/api/v1/player/[id]/index.ts:11`, `web/pages/api/v1/player/[id]/percentile-rank.ts:31`, `web/pages/api/SustainabilityStats/[playerId].ts:60`, and `web/pages/api/toi.ts:78` (the last two accept their inputs in the body). No caller identity is checked on these branches.

Exploit scenario: an unauthenticated caller selects a real NHL player without a current local roster row. A read triggers an external NHL fetch and privileged `players` upsert, even though the response then fails. The write does not populate the missing roster row, so repeated requests can repeat the operation. This is a constrained provider-derived write, not an arbitrary table/body write. Actual missing production IDs and deployment state were not inspected.

Suggested fix: keep the public reader side-effect free; return an unavailable/not-found result on a miss. Keep player hydration behind the existing authenticated maintenance entry point. No implementation performed.

### F2 — P2: rejected requests still cause privileged cron-audit inserts

Evidence: `web/lib/cron/withCronJobAudit.ts:262` awaits its inner handler, then unconditionally persists `cron_job_audit` at lines 367-369. For example, `web/pages/api/v1/db/update-nst-team-daily.ts:933` exports `withCronJobAudit(adminOnly(...))`; a 401 response from the inner wrapper does not prevent the subsequent insert. The complete set of **96** outer-audit exports is marked `A!` in `API-ROUTE-INVENTORY.md`. `internal/sync-yahoo-players-to-sheet.ts:42` similarly places its internal cron check inside the audit wrapper.

Exploit scenario: a caller without credentials repeatedly requests one of those routes. The business operation remains denied, but each rejection can still allocate a service-role database audit row and associated runtime. `details.url` also records the request URL at `withCronJobAudit.ts:343`; arbitrary attacker query strings enter this audit field. No secret-bearing request was sent or read.

Suggested fix for unfenced ownership: make authentication outermost and perform audit work only after admission, following the already-existing ordering at `web/lib/cron/withOperationalRouteAuth.ts:100-129`. If rejected-request security telemetry is desired, explicitly bound and isolate it from this operational writer. **Fenced consumers (`run-projection*`, `run-*forge*`, and any fenced helper impact) are for Claude session only; no fenced edit is proposed here.**

P6 reconciliation: its final report changes only `update-nst-team-daily.ts` and its test; the audited route hash is `af40a7562ab28f004f2d3dc363fa6fc25f06015fc3e63c3642865ec60edf9fac`. The unchanged wrapper hash is `c747280dd09aa4ba40f59bfb06b72ff42df20cbb31bff575d952d57826a36ff0`. Both match `cron-c0076/P6-HANDOFF.md`; P6 did not create or resolve this preexisting authorization-order issue.

### F3 — P2: legacy fragment sessions bypass PKCE transaction binding

Evidence: `web/pages/auth/callback.tsx:174-179` and `web/pages/auth/reset-password.tsx:211-216` accept supplied access/refresh fragments and call `supabase.auth.setSession` without first proving an initiating browser transaction. `web/lib/supabase/auth-callback-location.ts:137-138` captures those fragment fields. PKCE selection at `client.ts:19` governs new code-based flows; it does not enforce a verifier on this explicit compatibility branch.

Exploit scenario: an attacker obtains valid tokens for their own FHFH account and persuades a victim to open a crafted callback fragment. The victim's browser can adopt the attacker's session. Later activity or private imports can be saved into the attacker-controlled account. The reset route has the same account-confusion exposure. This does not show that an attacker can forge tokens or acquire the victim's existing session.

Suggested fix: after the explicitly required full Google completion/compatibility decision, retire the unbound fragment session branch, or require a securely bound, expiring initiating transaction for the remaining compatibility flow. The task list explicitly retains fragment compatibility pending that provider gate (`tasks/TASKS/auth-user-settings-platform/tasks-prd-auth-user-settings-platform.md:344`); this review neither closes that gate nor authorizes a live flow.

### F4 — P2: Patreon account linking has signed state but no browser binding

Evidence: `web/lib/integrations/patreon/oauth.ts:123-175` issues/verifies a signed user ID, next path, timestamp, and nonce. The nonce is neither stored/consumed nor bound to a browser cookie. `web/pages/api/v1/account/patreon/callback.ts:23` verifies that state, and line 51 links tokens to `state.userId` without validating the browser's current FHFH account or a browser transaction.

Exploit scenario: an attacker legitimately starts Patreon linking from their own FHFH account, then sends that authorization URL to a victim. If the victim approves using their Patreon account, the callback can attach the victim's Patreon identity/tokens to the attacker's FHFH account. The signature prevents state forgery; it does not prevent transferring an attacker-created authorization flow to another browser. Victim provider approval is required; no provider flow was exercised.

Suggested fix: bind the initiating user and state to a short-lived, single-use server transaction plus an HttpOnly browser cookie, and require that binding before exchange/linking. Yahoo's existing transaction/cookie flow (`web/lib/integrations/yahoo/oauth.ts:85-158`) is a local reference for the ownership pattern; provider capability changes are not assumed.

### F5 — P2: Patreon return-path validation permits a tab-normalized off-site redirect

Evidence: `web/lib/integrations/patreon/oauth.ts:95-110` rejects literal `//`, backslash, CR and LF, but permits TAB; `buildPatreonAccountRedirect` returns the resulting string at lines 392-400. The callback passes it to `res.redirect` at `web/pages/api/v1/account/patreon/callback.ts:55,69`.

Pure local fixture `patreon-return-fixture.cjs` extracts only those two pure functions, without importing config or executing OAuth/provider code. Input `"/\t/attacker.example"` is preserved by the sanitizer; after status/query assembly, WHATWG URL parsing resolves its origin to `https://attacker.example`. Node's header-value validator accepts the resulting `Location` value. Receipt: `patreon-return-fixture.json`, source SHA `d601718f6225cf4880adf53a346be97feec094421b0552f469ba54f5057285ca`. No browser navigation or HTTP server was used.

Exploit scenario: an authenticated attacker requests a Patreon flow with that return path and causes a valid callback/state branch to redirect to an external site, supporting phishing or redirect-chain abuse. Platform/provider enforcement of the entire flow is unverified; the sanitizer/URL normalization defect is reproduced locally.

Suggested fix: validate the parsed URL's origin against a fixed same-origin base and reject control characters, then serialize only a safe pathname/search. Reuse the Supabase callback return-path pattern where suitable, with narrow regression coverage. No implementation performed.

## Auth controls that are already present

- Browser client: explicit `flowType: "pkce"`, `detectSessionInUrl: false` (`web/lib/supabase/client.ts:16-19`). `lib/supabase/index.ts:15` reexports that shared client. The separate token-auth client disables session persistence/refresh (`index.ts:34-45`); it is not a second OAuth initiation flow.
- Callback/reset consume and scrub query/hash credentials and Next history URL/as fields **before awaiting** exchange or verification (`auth-callback-location.ts:103-139`; callback lines 75-89; reset lines 139-156). The Supabase return sanitizer checks parsed origin, rejects recursive callback/reset paths, strips auth query keys and fragments (`auth-callback-location.ts:73-97`). Exchange/OTP/failure paths use generic error text.
- Existing focused scrub/return test: `npm test -- lib/supabase/auth-callback-location.test.ts --run`, from `web/`: **PASS, 13/13, exit 0**. Test and Vitest setup were inspected; this test imports only the pure location helper and uses synthetic DOM/history data. Setup does not load local environment files. Chef separately reports the same independent 13/13 pass.
- Yahoo connect requires a verified user and stores a PKCE verifier/state/browser-binding hash transaction (`oauth.ts:85-158`). Callback consumes the browser-bound transaction before provider exchange; return paths reject backslashes and controls (`oauth.ts:51-67`). No hosted RPC behavior or live provider completion is inferred from source.
- API user guard validates bearer tokens using `auth.getUser` (`lib/api/requireApiUser.ts:20-43`). Admin guard binds role lookup to that verified user, fails closed on missing cron configuration, and restricts the local exception to explicit development plus loopback peer/local forwarding (`utils/adminOnlyMiddleware.ts:15-130`). Forecast editor guard adds runtime boundary, exact configured allowlist and admin lookup (`utils/playerForecastSeasonEditorOnlyMiddleware.ts:48-105`). These are source findings, not RLS/provider deployment evidence.

## Inventory method and acceptance

`API-ROUTE-INVENTORY.md` has one row per API source file, with methods, auth/branch classification and effect-site IDs. `source-inventory.json` pins all 968 import-closure modules by SHA-256 and records sanitized import/guard metadata. `resolved-helper-closures.json` separately records conservative identifier/default-parameter/callback expansion; `effect-sites.json` and `route-classifications.json` deduplicate and relate the 614 reviewed callsites. `browser-reachability.json` covers 544 page/component/hook/context roots, removing erased type-only imports before identifying 17 candidate dependency chains. Server page pruning and final bundler tree shaking were assessed separately, not silently assumed by that scan.

The import closure is **not an executed call graph**. Factory action branches were checked explicitly; generic computed RPCs remain `RPC_DYNAMIC_EFFECT_UNKNOWN` rather than asserted writes. Fixed non-reader RPC dispatch is listed separately from direct writes. Direct and helper-closure callsites are source evidence; dynamic injected receiver implementations and hosted SQL/provider behavior remain bounded unknowns. Complete route enumeration is established; this is not a proof of every possible runtime path, deployed ACL, RLS policy, provider state, browser artifact, or absence of all vulnerabilities.

No application code was edited by P8. Shared `git diff --stat -- web` is nonempty because Claude/P6 changes predate this review; claiming an empty global code diff would be false. Source hashes are preserved for Chef's attribution check. No additional application tests/type/lint/build were needed for report-only output. No process remains running.
