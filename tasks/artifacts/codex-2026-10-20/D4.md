## Confirmed direction and source risks

The [Supabase announcement](https://github.com/orgs/supabase/discussions/45329), verified October 20, sets October 30 for opt-in grants on **future public objects**. Existing object grants remain; custom schemas are outside that platform change. [Current API security guidance](https://supabase.com/docs/guides/api/securing-your-api) distinguishes object privileges from row policies. This packet addresses both missing explicit grants during reconstruction and excess grants inherited from baseline defaults; it does not predict a blanket October 30 outage.

Root `supabase/config.toml:13` exposes `public`, `graphql_public`, and `analytics`; it is the canonical config, while `web/supabase` is historical. `extra_search_path` does not equal exposure. `analytics`/`graphql_public` object ACLs and views remain UNREVIEWED. No config was changed or local CLI startup/root resolution claimed.

The baseline at `20260716112908_production_schema_baseline.sql:44814-44825` grants broad table, sequence and function defaults for creator **postgres**. A plain canonical replay can restore that posture. A late `ALTER DEFAULT PRIVILEGES` affects future objects only and cannot remove earlier ACL entries. The candidate therefore treats future defaults and selected existing object ACLs separately. It must follow, rather than rewrite, applied history after approval.

Broad baseline defaults can leave service UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER. The candidate first revokes all four grantees, then grants SELECT/INSERT. This is a **proposed narrowing**, requiring caller review and replay; source text alone is not a live defect report.

## PUBLIC, creator defaults, RLS and views

The proposal revokes table/sequence/function automatic grants for future objects created by **postgres in public**, with no automatic replacement service grant. Every future object needs explicit per-object grants bundled with RLS/policies. It also proposes a **global creator-role** default revoke of PUBLIC function EXECUTE: schema-local default revocation cannot subtract PostgreSQL's global PUBLIC function default. That line affects future postgres-created functions in every schema, so it needs explicit review before extraction. It does not revoke existing function grants or guess other creator roles such as supabase_admin.

`has_*_privilege` tests check each operation individually and see inherited PUBLIC/role permissions; comma-separated privilege strings are not used as an all-privileges assertion. Separate `aclexplode` assertions require PUBLIC EXECUTE to be absent for every reviewed RPC. Catalog validation must inspect memberships, owners, column ACLs, `pg_default_acl`, `pg_proc.prosecdef/proconfig`, policies and grants. Candidate SQL only reconciles selected object-level ACLs; column-level grants or privileges inherited from non-PUBLIC parent roles would need separately reviewed revokes. Tests should expose effective permission mismatches rather than assume those revokes are enough.

RLS governs rows after object/schema access. It does not govern function EXECUTE, and SECURITY DEFINER can bypass caller RLS. Views may run with owner permissions; for an exposed view review its `security_invoker` setting (Postgres 15+), underlying table/RLS behavior, owner and intended role grants. No blanket anon SELECT or authenticated write grant, no new SECURITY DEFINER function and no view exposure is proposed. Exposed analytics/views remain explicit readiness blockers.
