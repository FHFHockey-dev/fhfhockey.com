## Actionable source finding

Automatic dispatch already exists in `web/hooks/useCandidateMetrics.ts:8-36`: a non-null snapshot starts a Worker and posts a fresh calculation intent containing `steps: []`; changing selected steps does not trigger or gate this calculation. `candidatePlanMetrics.ts:37-58` builds the original-roster baseline and calls the existing `candidateAcquisitionSteps` generator for each selected verified available candidate. That generator (`planning.ts:993-1040`) creates timed add, reserve/add and drop/add proposals. The existing evaluator re-optimizes them privately. This is already the required direction: suggestions before user selection.

The missing runtime evidence is where that existing path stops for TJ's displayed candidate. `CandidateCard.tsx:51` uses one generic message whenever `plan` is absent. `CandidateBrowser.tsx:57-58` can have no comparison because the broader displayed catalog does not match the exact worker snapshot, the candidate was filtered, or the bounded frontier omitted it; a present comparison can also contain zero retained plans. Hook loading/failure and stale-response invalidation produce no metrics as well. No claim of a missing automatic trigger or repaired suggestions is justified yet.

A bounded-search edge deserves a regression: `candidatePlanMetrics.ts:93-104` counts skipped add-only proposals toward the per-candidate cap (default 12), and `planning.ts:1020-1034` visits the first two drop choices for each date before later drop choices. Early invalid drop/reserve choices plus several dates can consume the cap before a later legal drop. A no-plan result with an unexhausted iterator is a search-limit state, not proof that no legal acquisition exists. This is a static hypothesis, not a demonstrated defect or proof of TJ's actual state; do not increase bounds or change generator fairness before the regression establishes it.
