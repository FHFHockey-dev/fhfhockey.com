## Decision

Propose one separately named, authenticated **POST** job, `refresh-roster-optimizer-schedule`, at **09:50 and 21:50 UTC** (`50 9,21 * * *`). Use the repository's documented **pg_cron → pg_net → web route** convention, subject to confirming that operational ownership and the existing Vault reference before activation. Do not introduce a second scheduler or Vercel cron entry. No scheduler was created here. V2 requires an approved database transaction/trigger prerequisite before the writer can be enabled; it fails closed when the clock/RPC is unavailable.

Use a small recurring route, `/api/v1/db/refresh-roster-optimizer-schedule?profile=current-next-v1&dryRun=false`, with fixed recurring authority. Leave the existing exact-game/hash, one-time route untouched. Default requests to the new route are inspection-only; explicit `dryRun=false` enables a write after authentication, method enforcement and scope checks.

Two runs per day are the smallest simple cadence that tolerates one missed cycle while staying below the existing 36-hour cache gate: the next observation would ordinarily be 24 hours after the previous success. Daily execution can reach 48 hours after one miss. Two consecutive misses approach 36 hours and require operator attention. Execution delays and failures still matter; this is not an availability guarantee. This cadence **does not satisfy** the separate provisional 6-hour / near-puck-drop 2-hour UI warnings, and does not change or suppress them.

## Horizon and recurring authority

The proposed server-owned profile pins Yahoo game key **477**, Yahoo season **2026**, NHL season **20262027**, regular-season games and the existing cache conflict identity `game_key,source_game_id,team_id`. It does not infer season rollover from the wall clock or accept a caller-selected season, game set, date range, row cap or full mode.

1. Determine today's date in `America/New_York`, matching Start Chart's game-expectation scope and the NHL scoring-date use case.
2. Compute the full current and next Monday–Sunday calendar weeks.
3. Extend that range to include the **entire active Yahoo period** if its boundaries are wider. Exactly one valid active period is required.
4. Add one day of source-date padding on each side, consistent with the shared reader's date padding. Reject a horizon over 31 inclusive days rather than clipping it.

For the selected **October 12–18** week and ordinary Yahoo periods, every run during that week fetches **October 11–26 inclusive**: 16 dates, three source requests at October 11, 18 and 25. Thus October 12 does not age out of the refresh on October 15–18, and October 15 game `2026020112` is in scope. The offline fixture uses that supplied ID with synthetic teams/status/time; it is not a fresh observation of that real game's details.

This is a declared near-term service horizon, covering current/next calendar-week RSO and Start Chart dates inside it. It **does not promise freshness** for every arbitrary RSO selection (up to 367 days), a 21-day calendar request starting elsewhere, next-N discovery up to 60 days, all provider future periods, historical workspaces or all possible manager timezones. A selected range outside the refreshed horizon keeps its actual receipt ages and existing limitations; its extension requires a separately bounded decision. A wider active provider period is included only while the 31-day cap holds. Season edges, missing calendar mappings or a new season stop writes and require review.

## V2 database enforcement and prerequisite

[database-prerequisite.sql](database-prerequisite.sql) proposes **four functions and two triggers**, installed atomically in one reviewed migration. It adds no table/column/index, changes no existing rows and is not an executed or pre-numbered migration. Generate the actual migration through the approved repository workflow only after authorization and reconcile it with the supported migration authority; do not paste this SQL into production from this proposal.

- A `BEFORE INSERT OR UPDATE OR DELETE` **statement trigger** obtains a nonblocking PostgreSQL transaction advisory lock, key `(20260829,161013)`, shared with the recurring RPC. Ordinary cache writer statements mechanically serialize; a contender fails with SQLSTATE `RS002`. This lock is in the database and lasts to transaction completion, across instances. No lock is held across NHL HTTP requests.
- A `BEFORE INSERT OR UPDATE` **row trigger** rejects `NEW.fetched_at <= OLD.fetched_at` on updates with `RS001`, using the row version PostgreSQL locks for that update. It also rejects null/non-finite or materially future receipts. This covers a direct legacy/manual upsert, not only the new RPC. The existing unique identity chooses the target; the trigger now controls which observation can replace it.
- `roster_schedule_observation_clock()` provides the ordering clock before recurring source capture. It is separate from the upsert transaction. Different capture phases may overlap, but the earlier declared observation cannot overwrite a later committed one. Equal clocks conservatively skip/reject even if payloads differ.
- `commit_recurring_roster_schedule(...)` takes the same lock, validates fixed season/key/date/side/byte limits, checks missing cached identities and newer/equal stored observations, then applies one complete upsert. A newer/equal side anywhere in the batch makes the **entire batch** a no-op. Its enclosing PL/pgSQL exception block rolls back changes before returning an acknowledged stale/busy/rejected result; it does not turn arbitrary SQL/transport failures into a skip. Row-trigger enforcement remains the final protection if any writer reaches a conflict update.
- RPCs and trigger functions use `SECURITY INVOKER`, schema-qualified relations/functions and explicit public/anon/authenticated revocation; only `service_role` receives execute grants. Existing table grants and RLS remain in place. Verify these permissions and the advisory-key namespace in an isolated database before a migration.

An applied acknowledgement reports the exact complete side count. `skipped_stale`, `skipped_busy` or `rejected` returns HTTP409, `success=false`, `writeOutcome=not_applied` and zero upserted rows, followed by the normal failure audit. A missing/error/partial acknowledgement remains `unknown`, even if the transaction actually committed. There is no automatic retry.

This preserves the one-time route's API query/hash/game/row/delete contract and requires no private-adapter change, but **it can now reject its stale/equal or contending database statement**. The route's existing failure/unknown handling and readback obligation remain essential. A multi-statement legacy full refresh is still multi-statement; this proposal does not make its chunks/deletions atomic. DELETE statements serialize but have no source observation comparison. Destructive/full-mode maintenance remains separately approved and outside the recurring guarantee; privileged owners disabling triggers or restoring/deleting data are outside this safeguard. Receipt order does not prove provider publication order or exclude a later upstream correction. Those limits must not be overstated as an all-purpose schedule-version system.

The finite adversarial harness models transaction/trigger semantics; it does **not** execute PostgreSQL. Before release, isolated real-PostgreSQL tests must establish the reviewer interleaving, both legacy/recurring directions, equal-clock duplicates, mixed-batch rollback, a busy transaction, `INSERT ... ON CONFLICT` row triggers, `READ COMMITTED` and higher-isolation failure behavior, privilege denial and lost acknowledgement. No schema deployment or database invocation was authorized or attempted here.

## Resource envelope and operational tradeoffs

Per scheduled invocation, with no retries, sequential source I/O and no downstream fan-out (capture phases of separate invocations can overlap; only database writer statements are mechanically serialized):

| Resource | Normal 16-date range | Hard proposed bound |
| --- | --- | --- |
| NHL source requests | 3 sequential GETs | 5 for at most 31 dates; no redirects/retries |
| Decoded source body | Measured only by fixtures here | 1 MiB/page; at most 5 MiB total; 8 seconds/page |
| Metadata reads / clock | 4 exact-count table reads + 1 scalar RPC | Weeks ≤64, season ≤1, memberships ≤64, teams ≤64: ≤193 accepted array rows; an overflow sentinel can return 194 before rejection; clock scalar is additional |
| Cache transaction | 1 commit RPC | Internal range read accepts ≤1000 sides (1001st sentinel rejects); newer-receipt check uses incoming identities; one ≤1000-side upsert; ≤1 MiB serialized row budget at route and stricter PostgreSQL jsonb text check; zero deletes |
| Audit writes | 1 on a write-mode attempt that reaches the handler | Existing `cron_job_audit` wrapper; inspection has none; auth/method rejections happen earlier |
| Handler deadline | No production latency measured | 90 seconds across metadata/source/cache/upsert, with abort propagation |
| Function / transport | Existing infrastructure | Existing 240-second route ceiling includes wrapper/audit; proposed pg_net timeout 120 seconds |

For the two scheduled calls/day this allocates **normally 6, at most 10 NHL GETs/day; at most 10 MiB decoded source/day; 8 metadata table reads + 2 scalar clock RPCs + 2 commit RPCs + 2 audit attempts/day = 14 external database requests/day; and up to 2000 upserted sides / 2 MiB serialized row JSON per day**. Internal SQL reads, indexes, trigger work and rollback cost are additional database work, not additional HTTP requests. No global request-rate limiter is proposed: extra authenticated/manual calls are outside this daily schedule allocation and each still incurs its per-invocation work before any busy/stale skip. The 1000-side cap is an approved hard allocation, not an observed population. Conditional arithmetic is 31 dates ×32 clubs ×at most one game/club/date =992 sides; ordinary16dates would cap at512 under that assumption. No actual normal population range was measured here, and the implementation does not assert that sporting invariant. Activation must record the source-derived expected count for its initial horizon rather than substitute these ceilings for observed counts.

Inspection retains five API array reads: ≤1193 accepted rows, potentially **1194** with the last overflow sentinel, plus the scalar clock. It calls no commit RPC and writes no audit. PostgreSQL's jsonb text rendering adds whitespace, so its 1 MiB check may reject a payload that passed the route's JSON check; it never truncates it.

Audit wrapper time lies outside the handler's 90-second timer; the existing configured function ceiling is 240 seconds and proposed pg_net transport timeout is 120 seconds. Neither a client abort nor function termination proves database cancellation; an in-flight RPC may commit and need bounded readback. The SQL has a one-second lock timeout for waits outside the nonblocking advisory gate, but no newly verified hard PostgreSQL statement-duration bound. Confirm deployed PostgREST/database cancellation and statement-timeout behavior before activation. Worst scheduled function wall-time ceiling is 480 function-seconds/day; this is not a CPU or dollar estimate.

There are no NST requests, rolling/FORGE pipeline calls, projection recomputes, data publishes, extra health-poll jobs, builds or deployments in this work. No pricing, deployed memory tier, actual CPU, transfer billing or pg_net version was queried. Dollar cost and savings are therefore unknown. The smaller horizon reduces source calls relative to the old 24-date default *per invocation* (3 versus 4); the proposed higher cadence means 6 versus 4/day, so this is not a net request-cost saving claim.

Metadata/cache row caps and the 1 MiB row-payload cap are explicit. The route/RPC response contains compact outcome/count/range/hash facts, no game/side arrays, a bounded duplicate warning and errors truncated to 1000 characters. Existing audit previews cap at 4000 characters. No general DB transport-body cap, exact SQL CPU/memory bound or savings claim is asserted. Earlier checks stop work rather than truncating data to look successful.
