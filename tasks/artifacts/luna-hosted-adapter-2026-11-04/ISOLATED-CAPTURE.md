### Stop semantics and outstanding reservations

A database stop serializes against new admissions and blocks new reservations. It **cannot recall an already reserved request**: the worker may already hold a reservation and may send or finish that one provider call after the DB stop commits. The route checks its in-process runtime gate again before dispatch, but that is not another database stop read. Environment/deployment changes are also not an immediate global cancellation guarantee.

Treat every outstanding reservation as potentially spent and keep the full reservation against the aggregate cap. On timeout, lost response or stop with an outstanding reservation, reconcile the existing job, attempt and provider/request receipt without resending or creating another job. Abort is not evidence that the provider did no work. A stop is therefore “no new admissions,” not “zero more in-flight activity.” The pilot's one-call/full-reservation cap bounds that residual exposure.

## Implemented scope

- New route: `web/pages/api/v1/sources/ifttt/luna-capture.ts`. POST returns 503 while hard-disabled; other methods return 405. No environment setting can enable it. Credential, scope and store callbacks are deliberately unconfigured. It imports no database client, existing receiver, processor or model code.
- `web/lib/sources/lunaHosted/capture.ts` provides an injectable handler. Next body parsing is disabled on this route, so the code gate and dedicated header authentication precede application stream consumption. The proposed credential is `x-fhfh-luna-capture-secret`, with constant-time comparison, 32–256 characters, and no query/shared-secret/Bearer fallback. No credential was created or read.
- It requires one configured policy UUID, applet label and source account, JSON UTF-8, at most 65,536 actual received bytes and a five-second body deadline. Declared lengths are checked, compressed content refused, malformed/aborted streams rejected. These are local per-request bounds, not total traffic/cost quotas or protection from infrastructure request charges.
- Existing receiver field aliases are accepted for text, username, post URL, publication label and optional embed/source account. Repeated decoded JSON names (including escaped equivalent spellings), unknown keys, multiple aliases for one field, missing required data and inconsistent account/URL claims are rejected. HTTPS X/Twitter status URLs are recognized without fetching them. This boundary is deliberately stricter than the legacy receiver; compatibility with a real applet is unverified.
- Exact raw UTF-8 content, SHA-256, byte length, server receipt time, configured scope, submitted metadata and a scope/post delivery key form a frozen versioned envelope. Publication labels remain unparsed; no timezone or publication authenticity is inferred. The envelope is versioned internally; no new version field is required in the unverified applet body. Raw payloads remain private and are never echoed in HTTP replies or logged by this module.
- `receivedAt` is this authenticated attempt's server timestamp sampled before body consumption. `firstReceivedAt` is copied from the attempt that wins the first durable retention and is immutable on duplicates; it is not the minimum request-start timestamp across overlapping arrivals. An earlier-started slow request can finish after a later-started winner, so both direct acknowledgments and reconciliation validate receipt timestamp syntax without asserting cross-attempt ordering. Neither field authenticates publication time. The future store must enforce this winner/immutability contract.
- A future private store may return baseline, exact duplicate, held variant or a durable policy refusal. The handler checks the archive receipt kind, UUID, scope, exact payload hash/length, delivery key, timestamp syntax and classification before acknowledging it. Every acknowledgment remains held for review, with sourceAuthenticated/canEnqueue/canPublish false.
- At most one write and, on exception/deadline/malformed acknowledgment, one exact read reconciliation occur. Each has a three-second application deadline and abort signal. Unknown reconciliation returns 503, never a second automatic write. Cancellation is not proof of rollback; late commits remain possible and require durable idempotency. Separate upstream delivery retries are not prevented by this handler.
