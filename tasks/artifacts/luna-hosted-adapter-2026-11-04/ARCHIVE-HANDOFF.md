### Stop semantics and outstanding reservations

A database stop serializes against new admissions and blocks new reservations. It **cannot recall an already reserved request**: the worker may already hold a reservation and may send or finish that one provider call after the DB stop commits. The route checks its in-process runtime gate again before dispatch, but that is not another database stop read. Environment/deployment changes are also not an immediate global cancellation guarantee.

Treat every outstanding reservation as potentially spent and keep the full reservation against the aggregate cap. On timeout, lost response or stop with an outstanding reservation, reconcile the existing job, attempt and provider/request receipt without resending or creating another job. Abort is not evidence that the provider did no work. A stop is therefore “no new admissions,” not “zero more in-flight activity.” The pilot's one-call/full-reservation cap bounds that residual exposure.

## Components and trust boundaries

- `lunaHosted/archiveStore.ts` is an injected backend RPC adapter. The existing capture handler owns the three-second operation deadlines and at most one exact read after uncertainty. The adapter validates the exact envelope before mutation, forwards the abort signal and never retries a write. A database rollback/timeout may leave no committed attempt; a committed but unacknowledged write is reconciled by exact scope/post/payload identity.
- Task-local `archive.sql` defines private `luna_capture.policy`, immutable `receipts` and immutable owner `approvals` and semantic `enrollments`. No policy or approval is seeded. A single finite policy row locks across retention, stop and quota admission. Bounds have proposed hard ceilings of 24 hours, 1,000 committed retention attempts, 100 receipts and 6,553,600 raw bytes. Actual values and the capture window require an owner choice; these are ceilings, not selected operating settings.
- Every eligible retention invocation consumes an attempt, including exact duplicates, malformed-envelope refusals and receipt/byte-cap refusals. Disabled, stopped, outside-window and already-exhausted requests do not change counters. PostgreSQL statement rollback also rolls back its counter; the application request limit and infrastructure-level traffic/cost controls are separate. Exact lookups are read-only and permitted after stop/caps to resolve uncertainty. The byte cap counts exact raw UTF-8 content; envelope/index overhead is additional, bounded separately by row size and receipt count.
- PostgreSQL independently checks the raw-body hash/size, decoded repeated JSON names, string-only allowed fields and aliases, configured account/post scope, metadata projection, delivery key and received timestamp. The SQL timestamp grammar now requires the same UTC Z form as the TypeScript envelope (calendar validity checked by PostgreSQL), and the URL /status/ segment is case-sensitive even when scheme/host matching is insensitive. Values such as now, numeric UTC offsets, 24:00 and uppercase STATUS are rejected directly by RPC. SQL URL/whitespace/range handling remains a conservative subset; unsupported encodings fail closed. Changed bytes (including whitespace) for the same delivered post produce an immutable held variant linked to the baseline. Exact duplicate attempts preserve the winning receipt and its clock.
- Backend `service_role` can execute only bounded retention and exact acknowledgment lookup. It cannot read archive bodies/tables, change policies, create approvals, load owner receipts or stage jobs. All tables enable RLS; explicit ACLs restrict the private functions. The privileged capture function is in the private schema with pinned search path, behind a SECURITY INVOKER public wrapper. These are machine-only role checks, not end-user auth.uid semantics. Deployed role ownership, PostgREST exposure and server timeouts remain to be verified separately.
- `load_for_owner(receipt UUID)` returns that exact immutable archive record. No browser/service-role loader exists. `stage_for_owner(approval UUID)` reads an immutable owner approval that binds the exact serialized draft, receipt hash, current worker approval ID, provenance and archived bytes. It atomically inserts the existing worker source/job without enabling the worker or reserving provider budget. Enrollment is keyed by worker approval ID, immutable archive receipt UUID (the receipt revision) and reference hash. New enrollment is serialized under the worker policy lock, limited by its max_calls (at most 20), and closed by its window/stop. Both enrolled rows and all jobs for that worker approval consume capacity, including held/completed jobs. Existing exact retries can reconcile after closure; they do not create capacity. A fresh approval/job nonce with identical approved bytes returns the original enrolled job ID. Divergent bytes at the same semantic key conflict. The returned job ID is authoritative, not a newly proposed nonce. Reconciliation verifies the original immutable approval plus all persisted job fields (including input/reference hashes), and exact receipt JSON/hash/provenance under row locks before reporting success. A changed archive binding or job/source conflict fails the transaction. The schema owner is trusted and necessarily has administrative powers; SQL cannot prove that an owner actually reviewed an original report.

## Truthful receipt and source review

`archiveReceipt.ts` defines a distinct `luna-isolated-review-receipt-v1` carrier using the actual `luna_capture.receipts` table name and actual archive UUID for receipt/event identity. The normalized inputRow is explicitly a projection of archived raw bytes plus a separate source review, not a fabricated legacy intake row. The archive payload, SHA-256, metadata, identity and clock are reconstructed and compared again by the shared review packet/mapper boundary.

The existing `tweetReviewSidecar.ts` and `tweetDecisionReviewMapping.ts` add this archive branch; normal legacy carriers retain their existing semantics. Missing owner source review and archive variants produce holds that the mapper reconstructs independently, even if a caller strips packet holds. No aliases, public state or source authentication can be granted by capture or draft preparation.

The first supported bridge is for a directly retained original report. A separate owner source review must bind receipt/payload/text hashes, post/account/canonical URL, verified publication time, reviewer, retained original-evidence reference and permission basis. Publication time is not inferred from the IFTTT display label. Relay accounts, unexpanded retweets, missing original evidence, conflicting metadata, impossible clocks and variants remain held. This slice does not invent quoted/original snapshots or turn applet credentials into reporting-source authenticity.

`prepareArchivedLunaDraft` defaults off. When explicitly enabled locally, it combines the owner-loaded record and source review with bounded dated identity/context, then reuses existing prospective draft and worker validators. It does not load, approve or stage anything. The owner must review the exact complete draft and insert a matching approval separately before owner-only staging. Full worker source, causal identity, hint and deterministic checks still run before admission; SQL staging is not a shortcut around them.
