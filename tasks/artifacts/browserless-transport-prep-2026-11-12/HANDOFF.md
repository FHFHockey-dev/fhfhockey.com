## Encrypted transport approach

Use an owner-controlled DNS name with a valid, hostname-matching certificate and a direct `wss` WebSocket upgrade endpoint on port 443. Retain the self-hosted service unless the owner separately chooses a provider migration. Do not simply replace `ws` with `wss` on the recorded IP/port: TLS listener, certificate, routing and service version have not been established.

The intended path is: web runtime → TLS on 443 → same-host loopback Browserless. If the proxy and Browserless are on different hosts, that hop must also use authenticated TLS or an explicitly reviewed encrypted tunnel. Do not send a token across a plaintext private network merely because it is private. Bind the plaintext backend to loopback, or remove it entirely with native TLS; block external access to its old port, including IPv6 and any alternate ingress. Exact DNS/proxy/firewall configuration needs the host owner's inventory and approval first.

Preserve the service's existing path/query requirements and WebSocket Upgrade handling. The TLS endpoint must upgrade directly, without 301/302/307/308 redirects. Before calling the result **encrypted-only**, prepare and review client enforcement: reject missing/malformed/non-`wss` URLs before connecting; reject userinfo/fragments if unused; restrict the intended host; reject redirects at transport level. A URL validator alone cannot neutralize Puppeteer's redirect behavior. Its current API accepts a custom `transport`; a bounded adapter with redirect following disabled is a possible implementation, but no adapter or dependency change is included here. Keep certificate/hostname verification enabled. Never use `NODE_TLS_REJECT_UNAUTHORIZED=0`, `rejectUnauthorized: false`, `--insecure`, or automatic fallback to `ws`.

Keep tokens in the approved secret store and runtime environment, never source, documentation, command arguments or diagnostic output. Query tokens can still reach proxy/access/error logs even over TLS. Require query-free access logging and safe proxy/Browserless/application error handling; do not assume application redaction covers the other layers. Authentication-header migration needs compatibility verification with the installed service version and all consumers; it is not assumed by this plan.

The next implementation's fixture gate must verify: valid `wss` accepted; missing/malformed/`ws`/HTTP/userinfo/fragment/unexpected-host inputs rejected before any socket; all redirects rejected, including `wss`→`ws` and cross-host redirects; certificate errors never bypassed; no automatic insecure retry; connection cleanup bounded; diagnostic/response payloads remain allowlisted. These enforcement tests are **planned, not implemented or passed**. This packet tests the current route's error handling only.
