## Verified findings

1. **Broad legacy grants persist.** All 398 ordinary public tables have RLS enabled. Of those, 269 grant both `anon` and `authenticated` SELECT, 21 grant SELECT only to `authenticated`, and 108 grant neither role SELECT; all 398 grant `service_role` SELECT. Among them, 106 give both browser roles SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES and TRIGGER. RLS blocks many row operations, so these grants alone do not establish an exploitable Data API write. However, [TRUNCATE and REFERENCES are not governed by RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), and remain excess SQL privileges even though no direct Data API TRUNCATE path was tested.

2. **Operational records are currently public-readable under the table policy.** `public.cron_job_audit` and `public.job_locks` each grant both browser roles all seven privileges above and have unconditional public SELECT policies. `cron_job_audit` includes a `details jsonb` column. With `public` exposed and the Data API enabled, the catalog indicates unauthenticated reads are permitted; actual Data API settings, existing row contents and sensitivity were not checked. The in-repo cron report reads the audit with a service-role client. `public.acquire_lock(text, interval)` is SECURITY INVOKER, executable by both browser roles and service_role, and its baseline implementation writes `job_locks`; its callers and required access need tracing before changing grants.

3. **The entitlement guard works differently from a permissive grant.** `user_entitlements` grants all seven table privileges to both browser roles. Owner SELECT/INSERT/UPDATE/DELETE policies are permissive, but `user_entitlements_draft_pro_service_only` is **restrictive**, adding a condition that excludes `draft_pro`, `patreon_supporter`, and `complimentary` provider rows for browser roles. Thus those protected keys cannot be created through the owner policy alone. An authenticated user can still insert, change, or delete their own other keys when the restrictive predicate passes; there are no non-internal triggers or key/status check constraints on this table. The current Draft Pro and in-season readers check the two protected keys, so this audit has not established a current paid-access bypass. The unprotected future-key surface merits an explicit server-only-write decision and local negative tests.

4. **Do not infer a view leak from a grant alone.** All 82 public views have `security_invoker=true`; 78 have effective SELECT for both browser roles. Two operational views, `cron_job_report` and `job_run_details`, include SQL command/return-message columns. Their underlying `cron.job` and `cron.job_run_details` both have RLS policies limiting rows to `username = CURRENT_USER`. Both browser roles have underlying table SELECT, and lack of `cron` schema USAGE alone does not protect a security-invoker view. Actual row ownership and API reachability were not tested; review these grants and retain needed service-role access.

5. **Future-object defaults are still broad today.** The catalog's `pg_default_acl` grants `anon`, `authenticated` and `service_role` all seven table privileges when either `postgres` or `supabase_admin` creates a public table; their public sequence defaults and public function EXECUTE defaults are also broad. Creator role matters. The pending local `20261020224500_data_api_explicit_default_privileges.sql` changes only `postgres` defaults for public objects and additionally revokes the global built-in PUBLIC EXECUTE default for functions created by `postgres` in **every schema**. That broader function change is separate from the announced table rollout and needs a dependency review, including RLS helpers. Do not infer the exact post-rollout ACL state for either creator without a fresh read.

6. **Security Advisor notices need interpretation.** The advisor reported 146 public tables with RLS enabled and no policy; this is informational and can be intentional for service-only tables. It also reported browser-executable SECURITY DEFINER functions `public.get_skater_game_scores_for_season`, `public.rpc_sko_player_series`, `public.verified_yahoo_player_identities_read`, and `analytics.rpc_sko_player_series` for both browser roles. Review callers, data returned, owner, search path and intentional exposure before changing EXECUTE or function security: [anon advisor remediation](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) and [authenticated advisor remediation](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). It separately reported public extensions, leaked-password protection, and a vulnerable PostgreSQL version; these were not investigated here.

## Local remediation sequence

1. Freeze current raw ACLs, relevant role memberships, column/sequence/function grants, RLS policies, view dependencies, creator roles and current consumer paths. Classify each targeted object as public read, owner read/write, authenticated-admin write, or service only. Treat the table inventory as a starting point, not an approved grant list.
2. Prepare a small **forward** migration for existing objects that are confirmed in scope and actually present. For `players` and `games`, preserve intended public SELECT and the current authenticated-admin write contract; remove unnecessary anon write/non-row privileges and verify service consumers. For `cron_job_audit` and `job_locks`, propose no browser access and only individually traced service operations, including the invoker lock function, if the owner confirms those operational records are not a public product surface. For account tables, preserve only the owner-scoped operations that client flows actually need; propose server-only entitlement writes after tracing consumers. Review the two cron views and the four flagged SECURITY DEFINER functions independently. Do not grant all roles on all tables or create blanket `USING (true)` policies.
3. Separately reconcile migration history and choose a new reviewed candidate for the existing D4 intent. Split present-object changes from absent feature objects; do not edit or rerun historical migrations in place. Record exact ACLs for per-object rollback. Review any proposed default-privilege change separately from existing-object grants, including `postgres`, `supabase_admin`, sequences, global PUBLIC function EXECUTE and policy-helper dependencies.
4. For every future table creation, put explicit role grants next to the table's RLS/policies and revoke any unwanted pre-existing defaults for the roles concerned. For the FORGE candidate, coordinate with its owner on revoking service_role's inherited extra privileges before re-granting only the required operations. Preserve the RSO purge DELETE and execute contract if that feature is separately authorized.

## Test packet and gates

The prepared [future-table-access.test.sql](future-table-access.test.sql) checks the two pending tables' effective seven-operation matrix, RLS enablement, purge EXECUTE and zero-row allow/deny reads. It is deliberately staged outside the shared migration/test tree. It **must** run only on a disposable local database after both candidate migrations are staged there; the FORGE service excess-privilege assertions should fail if broad old defaults remain. Zero-row reads do not prove row-level filtering.

On the same isolated database, extend the nearest existing `supabase/tests/data_api_grants.sql`, `data_api_grants_defaults.sql`, `data_api_grants_claude.sql` and `data_api_grants_rso_isolation.sql` tests only after scope/ownership is coordinated. Add synthetic users A and B and test:

- Public statistics: anonymous and authenticated SELECT return an intended fixture; anon writes fail, and authenticated writes work only for a verified admin. Service writes needed by producers still work.
- Private operational tables: anon and ordinary authenticated SELECT and all writes fail under the agreed matrix; the service-backed cron report and the exact invoker lock operations still work. Verify no unwanted TRUNCATE, REFERENCES or TRIGGER privileges through either direct or PUBLIC grants.
- Owner tables: A can read/update only permitted A rows; A cannot read or reassign B rows; anon gets no personal rows. Draft Ranker SELECT-only browser grants are intentional only if its service-backed mutation routes remain functional.
- Entitlements: authenticated A cannot insert, alter or delete protected `draft_pro`, `patreon_supporter`, or `complimentary` records; after an approved server-only-write change, A cannot write any entitlement key, while legitimate service issuance and reads remain functional. Do not assume RLS blocks TRUNCATE.
- New table creation under each actual creator role and the proposed defaults: check all intended role grants and RLS, denial of ungranted actions, required sequence USAGE for serial/`nextval`, and explicit EXECUTE for invoker functions and policy helpers. Run actual PostgREST/JWT fixture tests as well as catalog assertions; owner and service-role SQL can bypass RLS.
- Re-run current candidate D4 catalog and operational tests in migration-authority order, then compare fresh hosted metadata against the proposed forward candidate. Exercise no feature ingestion, purge, cron, provider, or production endpoints.

The installed Supabase CLI is 2.90.0; its help confirms `supabase test db --local` accepts test paths and `--workdir`. After preparing a separate disposable Supabase project, an example from `web/` is:

Do not substitute `--linked` or an unknown/shared database. No pgTAP replay or runtime Data API test was run in this audit: the Docker daemon was unavailable, the shared heavy-check lock was present, and the historical D4 harness path quoted by the ledger is currently absent. Existing historical replay claims are not fresh verification. One initial aggregate catalog query failed on a GROUP BY typo; the corrected query succeeded. The TSV shape/count checks passed.
