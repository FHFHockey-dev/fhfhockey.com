## Findings

No changes-required security defect found in the reviewed candidate. The edition API verifies `getUser(token)` before reading the exact verified user's stored role; only exact `social_editor` or existing `admin` passes. Metadata, cookies, submitted identity and alternate secrets cannot grant access through this handler. Duplicate/missing/erroring role lookups fail closed. Method/format/query denials precede protected source reads. All handler outcomes receive private/no-store headers and `Vary: Authorization`.

The browser gate withholds its child during rendered auth/role loading and denial, keys it by account, and unmounts it on sign-out or role withdrawal. A fast same-account role revalidation can batch the loading states without an intervening child unmount; automatic edition reload on token refresh is not guaranteed. Initial server rendering receives only format/time props; the default AuthProvider context prevents workspace rendering. This does not create a new server cookie architecture or change middleware bypasses. The bearer helper restricts URLs to existing relative edition formats, omits cookies, partitions pending work by user/token/URL, checks the current session after body decoding, and forgets settled work. AuthProvider's request sequence rejects older role outcomes and clears authority on both returned and rejected role errors.
