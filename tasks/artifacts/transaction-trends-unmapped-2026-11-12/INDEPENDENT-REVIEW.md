- **Inference supported by those observations:** 453 keys belong to Yahoo season 2024 and canonical season 20242025; setting the metadata admits these existing identities without fresh name matching or verification promotion. Continuity with 477 corroborates identity, while the game catalogue supplies the season. This does not classify the other sample records or prove a current unmapped total.
- **Direct write bounds:** the temporary manifest fixes exactly three player keys and three external UUIDs. Primary-key selectors, strict row loads, captured-value checks, conflict checks and row counts bound the two UPDATEs to three rows each. Direct field changes are source `season`; external `context_key`, `season_id`, appended `source_provenance`; the known trigger changes external `updated_at`. No direct ownership-history/current-season/canonical write exists. Existing provenance is preserved by concatenating an object after checking repair-key absence.
- **Concurrency:** source and external rows are locked for update; canonical, season and catalogue rows are share-locked. Relevant committed drift after the serializable snapshot can abort instead of silently overriding those rows. Uniqueness constraints provide an additional collision backstop. Predicate reads are not permanent exclusion locks against future conflicting inserts; serializable ordering can place the repair before a concurrent/new writer. Do not promise that this repair prevents later jobs from introducing conflicts or overwriting metadata.
- **Atomicity versus reversal:** an exception aborts the transaction; psql ON_ERROR_STOP and disconnection roll back its uncommitted table changes. Default execution still runs updates/triggers before ROLLBACK. A successful COMMIT is final; a later reversal requires a separately authorized compensating transaction with current-state guards. The retained before-values support preparing that transaction, but the candidate does not implement it. Nontransactional external trigger effects, if any, must be ruled out by metadata review.
- **No-op/idempotence:** all three completed rows bearing this repair ID cause zero UPDATEs; the admission check still runs. Zero or three complete rows are allowed; mixed/partial states abort. This is idempotence of metadata application, not authentication of every field in the appended provenance object: the no-op path validates its ID only. It does not rewrite a damaged repair object and should not be used as the sole audit of that object.
- **API relationship:** `ownership-trends.ts:253-279` reads exact full Yahoo keys from `yahoo_nhl_player_map_read` and removes conflicting NHL mappings. The SQL validates the underlying identity reader, not this outer view. The refreshed current view definition joins exact `player_key` to reader output, corroborating the checked-in August definition; a bounded actual-view readback remains needed after any authorized application. Historical keys need not appear in a current-season trend request, and a three-row admission repair does not prove a three-row change in a displayed aggregate.
