## Executable local candidate

`prepareForecastCadence` in seasonJobs.ts prepares immutable morning and separate per-game revision slots, normalizes timestamps, validates the authoritative required-source list and explicit source completeness/item counts/revisions, holds future/expired/started/unknown/inflight/successful slots, and proposes at most three attempts for failed-slot recovery. Three is the candidate finite recovery policy, not a claimed owner-approved live retry count. No existing endpoint or daily behavior calls the helper. It does not publish or enqueue anything and returns activationApproved=false. Late issuance retains its true decisionAsOf instead of backdating the 08:00 target. The existing legacy daily coordinator is unchanged.

`atomic-cadence-proposal.sql` is an executable review artifact, **not a source-authorized migration**. The repository migration-authority policy was inspected; no applied/source-authorized status was added. It targets only the existing season queue, adds one service-role-only opt-in morning enqueue function, and replaces its existing claim function with the same behavior except a three-attempt cap for the reserved `cadence:season:` namespace. A transaction advisory lock plus existing unique scope key prevent concurrent duplicate morning requests; existing successful/pending/running/failed slots are returned rather than reopened. Failed jobs use the existing not_before delay and lease path. Legacy watermark scopes preserve their behavior. Source timestamps alone never make the wrapper ready. The required-source receipt set must be established by the upstream producer owner; a caller-supplied receipt is not independent source verification.

SQL changes are not routed into hosted execution. The existing seasonal producer is not a native public FORGE release producer. Native `forge_game_update_queue` deliberately has a separate worker contract and lacks durable cadence-slot receipts across later news versions; its existing enqueue increments versions and its claim retries failures indefinitely until game start. Reusing season scopes for native game work would violate that boundary. That original native implementation gap is now addressed by the separate native increment; see native-approval-package.md for current code/SQL/evidence. Live activation and genuine input observation remain pending. Pure T−15 planning tests do not close that delivery gate.
