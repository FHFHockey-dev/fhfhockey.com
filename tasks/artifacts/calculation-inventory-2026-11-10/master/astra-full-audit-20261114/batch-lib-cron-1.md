## AFULL-CRON-W01 — one team's empty player source is certified as a complete game

- **Definition:** a finished game's complete player-stat source must contain observed participants for both teams before a complete-set replacement can delete omitted rows and certify completion. Aggregate nonemptiness is insufficient evidence of two-team coverage.
- **Source:** `web/lib/cron/gameStatsCompleteness.ts:419–474` requires six arrays but computes skater/goalie counts across both teams. It rejects only missing arrays or zero aggregate batches. `assertCompletePlayerGameStatsBatches:476–506` repeats aggregate nonemptiness. `transactionalGameStatsPersistence.ts:173–227,476–557` validates identities and lengths, but carries no side attribution or per-team completeness witness.
- **Concrete scenario:** a finished game's right-rail team source is complete; its boxscore contains a populated home team and `awayTeam: { forwards: [], defense: [], goalies: [] }`. All six arrays exist. Home has skater10 and goalie20 with otherwise valid source fields and parents. Source guard, processed-batch guard and transaction identity guard all accept. The helper uses supplied lengths as expected lengths, so omission is self-certified.
- **Actual reach:** single-game writer `web/pages/api/v1/db/update-stats/[gameId].ts:356–359,426–451` runs these guards and transaction; `getPlayersGameStats:615–719` flattens the two teams and discards side attribution. Season writer `update-season-stats.ts:708–711,769–794` has the same handoff. These were bounded source excerpts, not whole-route audit credit. No provider request or hosted occurrence was observed.
- **Persistence consequence:** terminal SQL147 `supabase/migrations/20261113190000_fix_team_goalie_game_stats_placeholders_nullable.sql:51–63` compares supplied array lengths with supplied expected counts. Its player rows lack team identity. At `393–411` it deletes existing skater/goalie rows absent from the supplied set, then `428–457` verifies supplied cardinalities and marks `statsUpdateStatus` complete. Thus a one-sided replacement can remove the other team's prior rows, or a first ingestion can leave them missing while claiming complete. This follows source control flow; no SQL was executed in this batch.
- **Evidence:** exact-source AST probe accepted the one-sided source and processed batches, and returned transaction player IDs `[10,20]`. Missing-source and both-teams-empty controls rejected. Probe runs only pure guards, not the handler, row-builder, repair function or RPC. SQL conclusion is separately static, using previously fully reviewed SQL147 plus the targeted ranges recorded here.
- **Affected readers:** complete game-stat consumers and scheduling/retry logic relying on the complete manifest can see incomplete counts as finalized; exact downstream pages have not been newly inventoried in this batch. Impact is reachable writer admission and complete-set replacement, not asserted live prevalence.
- **Suggested fix:** validate both teams' participant coverage before flattening and before any replacement; at minimum each side must have nonempty combined skaters and goalie participation for a finished game. Do not impose an invented fixed roster size or require forwards and defense separately nonempty. Preserve a meaningful source completeness witness through the handoff if completion is intended to certify more than that minimum.
- **Regression:** extend `gameStatsCompleteness.test.ts:195–227` with one side entirely empty, one side missing only goalie participation, and legitimate complete sides. Extend existing writer/transaction tests to assert no RPC or pruning handoff on that source. Current tests cover absent source and empty aggregate goalie batch, not one-sided nonempty aggregate. The transactional fixture itself uses one skater/one goalie and no side information, so it cannot establish team coverage.

## AFULL-CRON-W02 — quarantine accepts an exact prefix followed by a malformed row

- **Severity boundary:** proposed **P2 contract risk**, source-confirmed receipt-validator defect. No legitimate current SQL producer path to the malformed response was found; this is not a claim that current quarantine writes falsely succeed in production.
- **Source:** `transactionalGameStatsPersistence.ts:605–651` iterates returned rows, `break`s when a row is invalid (`620`), then tests only accumulated valid receipt count and sorted IDs. It never requires `rows.length === gameIds.length` or that every returned row was validated.
- **Scenario:** requested `[2025020001]`; returned `[validZeroCountReceiptFor2025020001, {game_id:999}]`. The first row is retained, the second breaks the loop, accumulated count/ID still matches and success is returned. Expected: reject the non-exact malformed set. Pure extracted post-RPC block returns one receipt for both the exact response and malformed-tail response; an extra *valid* row correctly rejects.
- **Reader:** `web/pages/api/v1/db/cron/update-stats-cron.ts:238–259` maps the accepted receipts to game IDs and advances the reported quarantine state through another exact-ID check, which cannot see the discarded row.
- **Producer containment:** baseline `quarantine_game_stats_v1` at `supabase/migrations/20260716112908_production_schema_baseline.sql:2753–2859` validates 1–10 distinct positive IDs, locks them, requires age/absence of partial stats/exact pending states, updates exact cardinality and returns only requested IDs with fixed outcome/version/zero counts/timestamp. That producer does not generate this malformed extra row. Other remote/schema/transport drift is unverified.
- **Suggested fix/regression:** require exact raw row count and reject immediately on any invalid row; extend `transactionalGameStatsPersistence.test.ts:318–363` with malformed trailing and leading rows, extra valid row and duplicate IDs. Existing tests assert exact receipt set and missing receipt rejection but omit invalid extra-tail input.
