## New provisional findings

### AFULL-DRAFT-W01 — selected ADP/position source and valuation/roster/summary inputs diverge (P2 proposed)

**Source-confirmed wiring; runtime and prevalence unverified.** `DraftDashboard.tsx:1709–1721` builds `rawPlayers`, then `allPlayers` by applying a Fantrax *league override* when present. The independent `adpSource`/`positionSource` selection at 1727–1754 builds `tableAllPlayers` from **rawPlayers** and selected Fantrax rows. It does not replace `allPlayers`. `availablePlayers` and `tableAvailablePlayers` likewise remain separate at 2199–2206.

The table and Suggested Picks receive selected-source players (`3714–3715`, `4218` region), and position multipliers/tier analysis use that selected table pool (`1750–1753`, `2328–2340`). However:

- Ordinary and personalized `useVORPCalculations` receive `allPlayers`/`availablePlayers` (`2349–2381`). The hook's ADP departure model sorts its input's shared `yahooAvgPick` field, takes the first `floor(picksUntilNext)`, then identifies best surviving position peers (`web/hooks/useVORPCalculations.ts:234–267`). That field can hold Yahoo or Fantrax data depending on which pool supplied it.
- Roster allocation uses `allPlayers` position/eligibility (`2283–2314`); VORP eligibility also comes from that pool through `web/lib/draftDashboard/playerValues.ts:21–33`. Position multipliers nevertheless come from `tableAllPlayers`, so the same valuation can use a Fantrax eligibility multiplier and Yahoo replacement eligibility.
- The summary and comparison modal receive `allPlayers` (`4414–4430`, `4479–4485`). Summary ADP highlights use its shared ADP field (`DraftSummaryModal.tsx:200–240`).

**Concrete scenario:** Pro user, no Fantrax league override, selected Fantrax ADP, fetched matching rows. Three eligible centers A/B/C have known values 100/80/60. Yahoo ADPs are 1/2/3; Fantrax ADPs are 30/1/2. One opponent pick remains. The displayed source says Fantrax, but VONA's parent inputs still predict A departing (Yahoo). C's best other survivor is B80, yielding `60−80 = −20`; using the selected Fantrax input predicts B departing, leaves A100, yielding `60−100 = −40`. For a recorded pick A at #10, summary reports Yahoo ADP1 and delta+9 while selected Fantrax ADP30 implies delta−20. The retained pure arithmetic receipt reproduces both branches without importing application code.

For positions, a player Yahoo C / Fantrax LW can display LW and receive LW weight while allocator and replacement pools still use C. The reverse inconsistency exists with an active Fantrax league override and Yahoo source selection: allPlayers can be Fantrax while the selected table uses raw Yahoo values.

**Expected invariant:** a named source choice must either govern each dependent measure or the differing basis must be explicitly identified at the consuming metric. This audit establishes divergent inputs and numerical consequences, not a new policy prescribing which provider is authoritative for each league. **Suggested fix:** define one effective pool per intended authority and use it consistently for dependent eligibility, ADP forecasts and summary; if the knobs intentionally affect only display, label dependent metrics' distinct source and avoid silently combining bases. Preserve real provider eligibility where that is the governing league rule.

**Regression needed:** an integrated parent fixture with intentionally different Yahoo/Fantrax ADP and C/LW eligibility, including a league override and selected Yahoo case; assert displayed source, VONA departures, multiplier, replacement eligibility, roster assignment and summary source. Helper-only mapping tests cannot pin the parent hand-off. No suitable full-parent source-switch oracle was established in this batch. Root owns acceptance/severity/ID reconciliation.

### AFULL-DRAFT-W02 — one-sided ADP deltas still produce both a “Steal” and a “Reach” (P2 proposed)

`DraftSummaryModal.tsx:178–261` initializes both extrema from the first ordinary pick with finite, truthy ADP and pick number. It maximizes and minimizes `overall − ADP` but never requires a positive steal or negative reach. Both rendered cards (`697–747` region) check only whether a player exists.

**Scenario:** the only ordinary pick is #10, ADP30, delta−20. Both extrema contain that same player, so the summary calls a 20-pick reach its **Biggest Steal** too. If all deltas are negative, the least-negative reach is still labeled a steal; all-positive deltas analogously create a false reach. Exact ADP ties likewise populate both labels. This is a signed-definition display error, independent of whether ADP is a qualified predictive measure.

**Expected:** a steal requires `pick > ADP`; a reach requires `pick < ADP`; if none qualify, show no qualifying pick or a neutral description. **Suggested fix:** admit only the appropriate signed deltas to each highlight (and explicitly handle ties), or label the extrema without asserting steal/reach. Keep keepers excluded and missing ADP unknown. **Reader reach:** the ordinary dashboard's Summary button and automatic completion summary, including its PNG export. **Test gap:** the inspected summary test has metadata/focus oracles only, no signed-highlight cases. Add all-negative/all-positive/all-zero/no-ADP fixtures to that existing test. No runtime executed.
