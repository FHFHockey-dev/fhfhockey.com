- Location/claim: `:1927–1938` (follow-up selection), `:1956–1987` (latest status), `:2105–2108` (completion note); distinct methods/query operations sharing a path must not replace one another's scheduled result.
- Evidence/scenario: a scheduled POST/action=all receipt at12:01 is continued. An extra successful GET/dryRun=true receipt on the same path arrives12:05. Exact `candidateMatchesSchedule` rejects that extra receipt. Nevertheless the job-summary callback picks it through `followUpAudits`, which checks only unassigned ID, routePath and UTC day. Baseline status continued becomes success with “Completed after 1 continued call(s).” Both IDs are marked matched. The concrete fixture uses the NST gamelog path and synthetic receipts; no assertion is made that this exact call combination occurred in production.
- Cause: the special continuation path weakens the canonical method/query/owner checks used by ordinary assignments. It also does not require the extra call to occur after the initiating continuation, or bind it to a persisted continuation ID/scope.
- Suggested fix: bind continuation receipts to an explicit execution/scope identity and validate method and operation semantics. Allow only documented cursor changes, not arbitrary same-path operations. Pin unrelated GET/query/manual receipts and a valid completion control; keep rejected extras visible separately.
- Readers/tests: cron report scheduled status, completion note, health counts and daily email. Existing ordinary assignment protection remains correct; the new counterexample bypasses it rather than refuting it. No email was sent.
