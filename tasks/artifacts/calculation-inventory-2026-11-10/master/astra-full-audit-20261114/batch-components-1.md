## AFULL-COMP1-01 — recovery from one invocation clears another invocation's failure

- **Severity:** proposed P1, reachable reader mismatch in operational health output. This is an incorrect recovery calculation, not merely a copy preference. Hosted occurrence was not measured.
- **Location:** `web/components/CronReportEmail/CronAuditEmail.tsx:119–129`, with `openFailures/recovered:130–131` and `allRecovered/headline:168–171`.
- **Claim checked:** “Earlier failures have recovered” and removal from “Needs attention” should require later success for the same method and full invocation route, including query parameters.
- **Evidence:** exact target component; exact target `web/pages/api/v1/db/cron-report.ts:1334–1338,1558–1612,2236–2282,2518–2524`; `/tmp/astra-components-1/probe.cjs`, exit 0. The current route differs from the target; the final trace explicitly uses its pinned Git blob (`9fdd3bbab1d7737ea245fb6f8a4aa78cff5aeec3fe15b720d22c0d7632dfbcbd`).
- **Wrong behavior:** failure groups key only by `jobName`, select the latest failure across all their routes, then select the newest `lastKnownSuccessDisplay` from any row. A different invocation's success can thus clear the latest unresolved invocation. The producer correctly keys success by uppercase method plus full canonical route, and unscheduled compaction preserves those distinct routes. The email discards that distinction.
- **Minimal scenario:** two GET failures named `rolling`: `/pipeline?batch=A` fails at 10:00, and its matched success is 12:00; `/pipeline?batch=B` fails at 11:00 and has no matched success. Both fit producer-preserved distinct query identities. Expected: A recovered, B remains open. Actual exact expression output: one recovered group whose latest row is B; `openFailures.length=0`; headline `Earlier failures have recovered.` The fixture sets auditFailures=2, cronFailures=0, omittedFailureObservations=0, complete totals, no competing alerts.
- **Affected readers:** daily cron email failure sections and headline. Producer success-history matching and the email subject's independent failure count are not changed by this component defect. The route supplies the component via `audits: [...auditBriefings, ...notableUnscheduledRuns]`.
- **Suggested fix:** share the producer's method/full-route invocation identity for grouping and recovery; use job-name fallback only when route unavailable. Repeated receipts may collapse only within that identity. Include identifying route/query in recovered output where needed.
- **Regression:** extend `web/__tests__/components/CronReportEmail/CronAuditEmail.test.tsx:260–275` with the two-query same-name fixture. Assert B remains in attention and the all-recovered headline is absent. Existing test checks two identical-route repeated failures and a different-name recovered job, so it does not catch this bug. It was read, not executed. Probe evaluates pinned initializers without app imports or email rendering; this establishes the wrong computed branch, not browser/email-client rendering.
