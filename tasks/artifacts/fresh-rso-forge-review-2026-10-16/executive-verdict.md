# Independent RSO / FORGE verdict — 2026-10-16

**The repository has credible building blocks, but not a reliably useful complete RSO workflow. The problem is not demonstrably “the forecast model” alone.** The shared forecast view can preserve honest next-game/next-N values, and the optimizer can find a good legal swap in a small complete fixture. Yet independent synthetic tests expose consequential failures *with perfect inputs*: bounded search misses beneficial swaps, and unresolved owned-player identity can produce a falsely quantified improvement.

The highest-priority findings are:

1. **Unknown roster contribution becomes a false gain.** An owned player with no verified current NHL team disappears from scheduled opportunities. The engine still certifies the remaining baseline as comparable. My fixture returned a **+10-point drop/add**, while its own drop ledger said the lost points and games were **unknown**. This defeats the intended “unknown is not zero” contract.
2. **The main candidate search does not reliably find the useful swaps it already knows how to evaluate.** With one candidate it found the correct **+9** swap. With 40 otherwise identical candidates, the default 160-evaluation budget tested only the first two drop choices; its best displayed swap was **−80**, while the legal **+9** option was never tested. A stronger 41st player was never evaluated because the 40-player set is selected by ID. Filters and Show more do not change that set.
3. **Connected category-league workflow is unfinished.** Yahoo supplies no opponent remaining projection. The visible manual matchup editor writes workspace fields that the connected snapshot does not consume. Separately, the primary candidate card disables every drop-containing category plan because it requires non-null net points, which category metrics never produce. Category utility is also deliberately unspecified, so “ranked net improvement” needs an explicit product decision for category leagues.
4. **Completeness and freshness are inconsistent.** The planning loader labels a fresh single team-game row “complete” without proving date/game coverage. FORGE’s forecast page retains loaded values without expiry invalidation; Start Chart has an expiry clock. These are separate from actual forecast accuracy.

**What I would pursue:** one daily-lineup, single-acquisition workflow, using the manager’s actual rules and a declared forecast basis: verify roster/schedule coverage → optimize the unchanged roster → evaluate complete drop/add pairs → show positive net improvements and tradeoffs before selection. Repair the identity/completeness contract first; prioritize/drop-bound the candidate work intelligently, and let a searched player be evaluated on demand. Retain the shared FORGE/Start Chart value contract. Do not silently zero unsupported scoring categories to manufacture a complete league score.

**What I would stop:** expanding multi-step search, adding more diagnostic disclosures, or growing issuance/review infrastructure as a substitute for this vertical slice. Do not undertake a wholesale model rewrite or loosen provenance checks on this evidence. Resolve the product meaning of category optimization instead of presenting schedule capacity as player-quality advice.
